# 第三章　流程改造：让岗位提效转化为业务结果

第二章讨论怎样围绕岗位目标拆解任务，并安排人、AI和程序的分工。任务分工之后，个人生产率提高、某一环节采用AI，未必带来团队交付和总投入的同步改善。本章先用研究与案例呈现这种落差，再分析修补、等待、资料与协作中的原因，提出相应改造措施。

## 3.1 现状观察：单点提效未必带来整体改善

DORA 2024年的软件研发调查发现，在统计模型中，AI采用程度提高25%，与个人生产率提高约2.1%相关，同时与软件交付吞吐下降约1.5%、交付稳定性下降约7.2%相关。交付吞吐衡量的是代码变更进入生产环境的速度与频率。[DORA 2024报告，第32、39—40页](https://dora.dev/research/2024/dora-report/2024-dora-accelerate-state-of-devops-report.pdf)

Dillon等人的随机现场实验覆盖66家公司、7137名知识员工，随机向个人提供集成式生成AI工具。按2025年11月修订稿摘要，六个月实验的后半段，使用工具的处理组员工每周邮件时间减少约两小时，但研究未检测到任务数量或构成的变化。[NBER工作论文33795，修订稿摘要](https://www.nber.org/papers/w33795)

具体业务中，还可以观察到产物交出以后需要补救、工作排队，以及资料与系统交接受阻等问题。

<a id="section-3-1-1"></a>
### 3.1.1 AI参与制作，完整交付仍然更贵

据服务方复盘，[兴城泳装商拍服务商](../下册-案例汇编/I-信息传输软件与信息技术服务业/I01-兴城泳装AI商拍服务.md#s-28-f01)在早期试点中已经用AI处理部分图像工作，但仍大量依靠PS补救，需要修图高手，交付成本反而比真人拍摄更高。这一阶段持续了近一年。

<a id="section-3-1-2"></a>
### 3.1.2 SKU增加后，待审核包装不断堆积

据实施者自述，[消费品企业包装审核](../下册-案例汇编/待定-行业待核/待03-消费品企业包装AI预检.md#c-19-f01)的原有流程中，SKU增加后，待审核包装不断堆积。设计、法规、渠道规范和产品表达等不同检查集中在同一条审核队列里。

<a id="section-3-1-3"></a>
### 3.1.3 工具与资料已经存在，仍要反复补充背景

[诉讼律师案件工作台](../下册-案例汇编/L-租赁与商务服务业/L06-诉讼律师AI案件工作台.md#c-03-f01)的实施者自述，起初提供智能对话入口，却发现律师每次提问都要重新交代案件背景。

[杭州市城市规划设计院](../下册-案例汇编/M-科学研究与技术服务业/M01-杭州市城市规划设计院AI辅助规划.md#c-04-f01)已有GIS等专业工具，综合报告仍需多个部门协调资料、图层与规则，再汇总核对。实施者在索取数据和业务规则时，还遇到回复慢、让实施方自行上网查找的情况。

<a id="section-3-1-4"></a>
### 3.1.4 物料找不到就重建，后续出现买错买重

[海外工业企业物料诊断](../下册-案例汇编/待定-行业待核/待01-海外工业企业物料诊断.md#c-08-f01)的实施者称，约十五个团队共用老ERP，同一物料存在不同名称、描述和单位。员工找不到已有记录就重新建档，重复数据越来越多；走访继续追到买错、买重、积压和报废。

<a id="section-3-1-5"></a>
### 3.1.5 一处已经完成，另一处仍继续执行

在2012年的传统自动化事故中，Knight Capital部署代码时漏更新八台服务器中的一台；其他组件已识别母订单完成，信息却没有传给订单路由系统SMARS，后者继续发送子订单。开市前97封错误邮件没有被设计成系统告警，也未被用于及时处理问题。美国SEC的行政令记载，事故最终造成超过4.6亿美元损失。[SEC行政令，第15—19段](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf#page=6)

<a id="section-3-1-6"></a>
### 3.1.6 各自有工具，跨团队连接与交接仍受阻

[面向东南亚的服装跨境电商项目](../下册-案例汇编/F-批发与零售业/F01-面向东南亚的服装跨境电商业务协同.md#c-22-f01)最初希望连接聚合SaaS与飞书，实施者却遇到共享接口凭据的约束：一个团队更新Key，可能影响其他团队的连接。

[基金公司研发培训](../下册-案例汇编/J-金融业/J01-基金公司AI研发培训.md#c-07-f01)中，研发人员已经分别使用AI工具，个人习惯形成后，统一工具遇到阻力；协作资料转向多份Markdown和TXT文件，又要重新安排文档怎样拆、产品与研发各写什么，以及多人修改怎样协调。

<a id="section-3-2"></a>
## 3.2 原因分析：为什么局部收益未必传导下去

完整业务包含准备、执行、交接、审核、修改与等待。局部节时能否留在最终交付中，取决于后续环节有没有增加修补、排队或重复准备。

制造业的工序协同为解释这种落差提供了一个参照。丰田生产方式强调工序同步，按需求安排生产，避免物品和信息滞留；发现异常时及时停止，防止缺陷继续流向后道。[丰田生产方式官方说明](https://global.toyota/en/company/vision-and-philosophy/production-system/)

对应到智力服务，分工后的任务也需要共同安排：上一环节交出的产物要符合下一环节的使用要求，提交量要与审核能力匹配，完成与异常信息要及时到达接手者。AI提高执行速度后，这些衔接条件也要同步检查，否则新增产出可能变成修补和积压。

<a id="section-3-2-1"></a>
### 3.2.1 修补与核验可能抵消前道节省

泳装商拍中的成本落差出现在生成之后的补救。生成图像还要核对衣服细节、形状和图像表现，才能成为可交付的商品图。即使生成更快，新增修图、核对和沟通也可能超过前道节省。销售方案同样如此：形成初稿以后，需求、价格和能力承诺仍需核实；完整投入要把这些工作一起计算。

<a id="section-3-2-2"></a>
### 3.2.2 前道产量与下游承接容量不匹配

包装审核中的不同检查需要不同依据与专业判断。若它们都进入同一队列，处理速度就受共同承接容量限制；只提高设计稿产量，可能只是增加待审数量。每份材料再需要更多查验，排队就会进一步延长。相反，若当前限制推进的是前道准备，准备提速才可能直接缩短流程。

例如，假设原来每天提交20份材料，审核也只能完成20份；提交量升至100份，审核仍只能完成20份，每天就新增80份积压。

<a id="section-3-2-3"></a>
### 3.2.3 工作依据没有延续，接手者反复重建背景

案件分析和规划选址需要的不只是一份文件，还包括此前的决定、限制、适用规则与未决条件。这些内容如果没有与案件或项目关联，下一次提问、换一个接手者或转到另一部门，就要重新查找和解释。各岗位分别用AI整理一遍，可能只是更快地重复准备；摘要增多也不能保证当前依据更清楚。

<a id="section-3-2-4"></a>
### 3.2.4 名称与判断标准不一致，错误沿业务链传递

物料检索与采购依赖对同一对象的共同识别。不同名称、描述和单位没有对应关系，已有物料就可能被当成缺货或新物料，重复建档继续影响下单和库存。AI即使提高检索与录入速度，若仍沿用各自的名称和判断标准，也可能更快地重复原有误判。

<a id="section-3-2-5"></a>
### 3.2.5 完成状态与异常未传达，后续动作无法及时调整

Knight Capital事故中的完成信息没有成为执行端停止的依据，错误邮件也没有促成及时处理。“某处已经记录”与“受影响的环节已经采用”是两个状态：完成、取消或批准的状态没有传到执行端，后续动作就可能继续；异常没有明确接手者，消息出现也未必带来处置。销售中的初稿、送审、批准和对外使用，同样不能共用一个含糊的“完成”。

<a id="section-3-2-6"></a>
### 3.2.6 访问条件与人员采用未协调，工具难以共同使用

共享接口凭据会让一次变更影响多个团队，工具连通还取决于权限由谁发放、凭据由谁维护，以及变化是否通知使用方。个人使用习惯也会影响共同工作：需求、Spec与其他产物由多个岗位共同形成，文档划分、修改和确认方式没有约定，下一位仍可能无法直接采用。个人节省的时间要支持更多协作任务，还需要相应的工作分配与接手安排。

<a id="section-3-3"></a>
## 3.3 改造举措：让单点提效传导到整体交付

针对修补、排队、背景重建与承接受阻，改造应同时落实交接标准、审核容量、资料依据和责任。业务负责人先沿实际工作记录找出当前受阻环节，再与上下游共同安排相应改动。

<a id="section-3-3-1"></a>
### 3.3.1 让交接的产物可以直接使用

让产物可用，先要由交出者和接收者共同说明：下一步需要什么，什么内容已经确认，缺项时怎样处理。

#### 举措1：共同确定交接内容与完成标准

销售与技术人员应一起确认方案准备所需的最少资料，包括客户目标、需求范围、限制条件、已作承诺和待确认问题；技术与审核人员再明确本轮审核对象、依据与需要作出的决定。对“已提交”“待确认”“审核通过”等状态说明工作含义，避免同一个词在各岗位代表不同进度。接收者发现缺项时，应指出影响哪一步、需要谁补充。

可以先用共享文档或表格记录这套约定，再让AI辅助对照材料、提示缺项。字段是否完整适合规则检查，需求是否表达准确、是否足以开展下一步，仍由相应业务人员判断。反复出现的缺项要反馈到交接模板和准备方法中，避免每次由下游重新解释。

标准要落实到接收者的实际工作。商品图需说明哪些实物细节不能改变，由谁对照验收；物料资料需确认同名异物、同物异名怎样辨认，谁有权新建；研发需求需说明业务、产品、研发分别维护哪些内容，修改以后由谁确认。先用少量真实产物走一遍，比只写“提高准确率”更容易发现分歧。

> **案例小贴士｜人的概念先对齐，工具才有共同标准。** [交个朋友虚拟IP团队](../下册-案例汇编/F-批发与零售业/F12-交个朋友虚拟IP内容生产.md#s-22-f01)在音频访谈中描述，AI首次给镜头打标签后，编导先讨论标签是否正确、统一含义，再把新规则交回工具重新标注，属于局部使用。

#### 举措2：让来源、版本与未决事项随产物交接

每次交出方案与汇报材料时，应同时说明本轮采用的需求记录、产品资料及批准依据。销售负责核对客户信息，技术人员说明方案依据，审核意见注明针对的版本；尚未确认的条件留在显著位置。接收者据此判断哪些结论可以继续采用，哪些需要先补资料或重新确认。

AI可对照本轮材料与原始记录整理出处、待确认项及修改差异，由交出者核实后随材料提供。重要数字和判断保留到来源的链接，并确认接收者能够访问。

> **案例小贴士｜从重新讲背景转到案件空间。** 前述[诉讼律师案件工作台](../下册-案例汇编/L-租赁与商务服务业/L06-诉讼律师AI案件工作台.md#c-03-f01)随后改为先建案、上传材料，再在案件空间检索与分析，属于局部使用。

#### 举措3：按岗位提供可用输入，并取得接收确认

共享同一项业务，不要求所有岗位看到或修改相同内容。技术人员需要需求与实现限制，商务审核需要价格和授权依据，履约团队需要批准承诺与执行条件。交出者应提供接收者能够使用的资料与权限，由接收者确认已收到、能够开展工作；存在格式不兼容、字段缺失或权限不足时，先明确补齐责任。

技术可以按业务标识关联记录、转换已有字段，并在授权范围内传递资料。AI辅助理解非结构化材料，程序处理规则明确的字段映射、计算和状态登记。识别与写入之后还要核对关键内容；资料送达、系统写入和业务接手分别留有记录，避免把发送成功当成交接完成。

> **案例小贴士｜将供应商单据转成ERP可用记录。** [女装批发企业](../下册-案例汇编/F-批发与零售业/F06-女装批发企业AI入库与工牌试制.md#s-35-f01)经营者称，供应商与自家ERP不同，采购单原需重新录入，局部使用拍照与OCR后，一次三四百个SKU的入库由约两小时缩到约二十分钟。

<a id="section-3-3-2"></a>
### 3.3.2 协调执行、审核与异常处理

交接内容清楚后，还要让工作量与承接能力匹配。能够直接检查的问题提前处理，需要专业判断或批准的事项交给相应人员；失败和返工能够返回原任务，才有机会减少排队与重复沟通。

流程负责人应先查看待审、退回和逾期记录，找出当前限制推进的环节。专业审核已经积压时，可以减少无必要的备选稿，按业务价值与期限安排提交，给符合条件的事项分配合适审核人；资料不足时，先补齐输入。是否增加人员或扩大自动处理，要根据任务质量与容量判断。仅要求审核人更快，无法解决前道持续送来缺项和错误的问题。

#### 举措4：在交接前处理可核实的问题

销售提交需求前核对事实和确认状态，技术提交方案前核对范围、数据与依据，商务材料对外前核实价格、交期和授权。业务负责人应区分哪些问题由提交者先改，哪些需要专业审核，哪些影响下一步必须暂停。预检要帮助审核人集中处理判断事项，同时保留正式审核要求。

固定计算、字段一致性和版本有效性可由程序检查，AI辅助查找缺项、矛盾和可能需要重审的内容。检查结果应附依据与待处理项，由提交者修订，再按要求送审。选择逐项复核或抽查，需要依据错误后果、检查能力及质量要求；预检通过只能表示约定检查项已处理，不能直接代替批准。

> **案例小贴士｜把可发现的问题放在专业审核之前。** 据实施者自述，[消费品企业包装AI预检](../下册-案例汇编/待定-行业待核/待03-消费品企业包装AI预检.md#c-19-f01)已局部使用：设计提交后先预检，固定计算用代码，结果附来源与置信度，复杂法规和产品表达由专业人员判断。

#### 举措5：按判断权限安排审核，并把决定送回执行环节

审核任务应写清请谁决定什么、所需依据是否齐备，以及决定影响哪些后续动作。负责人根据专业能力与授权分工，协调当前待审数量和期限；对重复出现且规则清楚的事项，明确哪些可按规则办理。方案获得批准后，还要把决定送回原任务和当前版本，销售、技术与履约人员才能据此继续执行。

任务模块可以保存待审事项、审核人、期限及结果，AI辅助汇总依据和待决问题；审批工具按授权分发，业务系统登记生效状态。需要区分审核意见已形成、批准已记录和下游已采用。客户反馈改变范围或承诺时，先判断是否重审，再更新受影响的任务与材料，避免用一次批准覆盖后续所有修改。

> **案例小贴士｜正常事项继续流转，例外交给人。** [浙江车管所](../下册-案例汇编/S-公共管理社会保障与社会组织/S01-浙江车管所AI网办审核.md#c-02-f01)的实施者称，材料识别接入既有系统操作，正常业务继续流转，异常交人处理，项目已使用并通过验收。技术还使过去人工放宽的审核尺度显现，由业务管理方决定采用什么规则。

> **案例小贴士｜审批通过以后，还要回到原系统。** [Odoo与飞书审批回传](../下册-案例汇编/附编B-原型与演示参考/附B07-Odoo与飞书审批回传演示.md#s-16-f01)在一次配置演示中，把订单字段送入两级审批，再回传Odoo并触发订单确认。

#### 举措6：让缺项、失败与更正返回有责任人的任务

资料不足、执行失败、审核退回或客户变更时，应说明发生在哪一步、影响什么、已有产物还能否使用，由谁补齐或重新决定。需要停止后续动作的，及时暂停；完成更正后，再核实关联记录与接收者是否已更新。例外不应只留在群消息里，也不能通过私下绕过权限和业务规则解决。

系统应记录失败及当前状态，区分未执行、执行中、已完成和待核实的结果。AI可以整理错误依据、提出排查或修订建议，但业务动作是否完成要看原系统返回与必要核验。自动重试应先检查实际状态和重复处理风险；无法确定时，交责任人处理。正式更正路径、历史记录保留和重新交接，要一起纳入验证。

> **案例小贴士｜异常处理遵循原系统的正式路径。** [ERP核价单更正演示](../下册-案例汇编/附编B-原型与演示参考/附B06-ERP核价单更正演示.md#s-15-f01)使用测试数据：10元核价单审核后被锁定，修改等操作未成功，最后新建5元单并审核，旧单保留但不再引用。

<a id="section-3-3-3"></a>
### 3.3.3 建立组织上下文，明确权限与安全要求

资料、决定与当前进展分散在各处，接手者就要重新询问背景、辨认有效版本。交接标准和审核分工确定后，还需要围绕同一商机、订单、案件或项目，把产品与制度等可复用知识，同已确认需求、决定依据、有效版本和接手责任关联起来，并随业务推进持续更新。这些供各岗位接续使用的知识与业务事实，构成**组织上下文**。

#### 举措7：围绕业务对象关联依据、决定与当前状态

企业可以先为商机、订单、案件或项目确定稳定标识，关联原始资料、已确认事实、重要决定、有效版本、未决事项和当前责任人。各岗位维护自己负责的内容，交接时说明下一步采用哪份依据；发生变化时，通知受影响的人和任务。这样，下一位可以接着已有工作继续，而不必向每个参与者重新询问背景。

原始资料可以留在客户管理、ERP、文档或其他合适系统中，由共同入口定位。AI可以按任务查找获准资料，整理带出处的背景、变化和缺项；业务系统保存正式状态，负责人确认重要事实与决定。摘要应能回查原文，检索结果应带版本及有效时间。查不到、无权访问和资料已过期，需要分别返回给任务，不能默认为“没有这项事实”。更具体的索引与维护思路见[附录D](附录D-知识网络建设细节.md)。

客户改了交期，变化应到达方案、报价和履约安排；审核退回，任务应回到明确的修改人；接收者发现关键依据不足，应能退回补齐。

#### 举措8：按任务确定可见、可改、可批准与可对外提供的范围

完成同一笔业务的岗位，所需资料和操作权不同。业务负责人应与资料负责人共同确认每项任务需要哪些内容，哪些只可查看，哪些可以修改，哪些动作需要批准，以及结果可以发给谁。跨部门或外部服务参与时，应明确授权责任人、范围、期限和撤回方式；缺少关键资料时，安排申请或由有权人员提供必要信息。

> **问题与安排｜数据权限协调本身占用时间。** 据实施者自述，[TikTok达人运营试点](../下册-案例汇编/L-租赁与商务服务业/L01-TikTok达人运营AI协作.md#c-05-f01)获取业务数据时，申请经历退回和重新提交，权限协调耗时约一个月。

> **案例小贴士｜同一张订单，字段与操作权各有分工。** [制造企业订单与岗位权限调整](../下册-案例汇编/C-制造业/C05-制造企业订单与岗位权限调整.md#s-06-f01)的试点培训中，车间按工况调整长度与支数，价格由下单端控制，办公室核对时需要看到合同价格，后续工序单据送到对应岗位。

系统连接应按这些范围校验当前发起者和执行服务的权限。AI能够检索资料，不等于可以改价、下单或对外承诺；可读源文件，也不等于可把内容复制到所有人的群聊。对于有权参与但无需看全部资料的岗位，可以提供经过核实的必要字段或脱敏结果。授权规则由组织确定，程序落实检查，AI负责在获准范围内辅助工作。

#### 举措9：让权限约束继续作用于检索、摘要和结果交付

资料进入共同检索以后，原来只在一个岗位或项目内使用的内容，可能随摘要和报告进入新的接收范围。企业需要同时判断谁有权取得依据、结果可以送往哪里。访问边界应继续约束引用片段、摘要和报告：不能只控制原文件，再把受限内容放进人人可见的摘要。客户之间、项目之间的资料应按约定隔离，对外材料需要核实接收对象和可披露范围。员工转岗、退出项目或外部服务结束时，应调整相应访问，并处理按约定需要撤回、删除或限制使用的副本。

技术实现应让检索按当前身份和任务权限筛选资料，让摘要、缓存与导出结果保留相应访问约束。外部模型或服务参与时，要确认发送哪些内容、如何保留、谁可访问以及何时删除；任务不需要的个人信息和商业敏感内容，可以在发送前去除或脱敏。权限改变后，原文入口和已生成副本都要按约定检查，不能只撤掉一个系统账号就认为全部访问已结束。

邮件、网页和客户附件可以提供业务事实，其中夹带的操作要求也需要核实来源。外部材料要求转发内部资料、改变收件人或修改业务规则时，应先按现有授权检查，不能让材料中的文字自行取得执行权。检索、审批和对外发送分别留下必要记录，便于查清用了什么依据、发给谁以及谁作出决定；日志本身同样需要访问与保留范围。

#### 举措10：给系统连接、变更和失效安排责任人

跨团队连接需要明确谁维护账号与接口凭据，谁批准变更，变化前通知哪些使用方，失败后谁接手。针对前述共享Key的约束，可以评估服务是否支持分开授权，或通过受控连接统一管理；无论采用哪种方式，都要验证变更会不会中断其他团队。中转数据库、自动化平台和服务账号自身也有数据副本与操作权，需要纳入同一套管理。

[跨境电商项目](../下册-案例汇编/F-批发与零售业/F01-面向东南亚的服装跨境电商业务协同.md#c-22-f01)在交付后由客户移除实施方权限。实施结束时，日常维护应交由客户侧或获准服务方承接，权限收回与后续责任交接一起安排。

正式改价、下单、发布或对外提供敏感资料时，应按业务后果确定检查和批准要求，并限制执行对象与范围。连接失败、返回不确定或状态不一致时，要有暂停、核实与恢复路径，避免重试造成重复操作。验收既要检查有权人员能否取得所需依据，也要检查越权访问是否被拒绝、权限撤回是否生效，以及异常是否到达责任人。维护和安全处理属于完整运行投入。

上下文贯通后，还需根据待审数量、一次通过率和实际采用情况，调整审核与执行的分工和容量。

<a id="section-3-3-4"></a>
### 3.3.4 沿同一业务对象检验完整交付

验收时要沿同一业务对象，跟踪从约定起点到终点的完整过程。以销售方案为例，从需求交出、方案准备与审核、客户反馈处理，跟踪到客户确认方案、签约或履约验收；本轮终点按改造范围事先确定。

#### 记录完成、等待与返工

为每项业务记录进入和离开关键环节的时间、接收确认、退回原因、修改次数和最终产物。将实际处理时间与等待时间分开，区分等待内部资料、审核、客户决策和其他原因。负责人据此判断：资料准备是否减少，审核是否积压，返工是否前移或减少，产物是否真正被下一环节采用。

已有业务系统能提供记录时，先使用现有数据；缺少时可用简表补记。AI辅助归纳停滞与退回原因，但判断应回到原记录及参与人员。前后比较采用相近的业务类型、难度、交付范围、质量要求与观察期，并记录尚未结束的事项。

对上下文贯通，还应记录下游是否重复索要资料、是否用错版本、重要变更是否到达、缺项能否找到补齐人。权限等待区分必要审查与无人接手，安全测试按约定范围验证。

> **案例小贴士｜从合作确定追到内容提交。** 据实施者自述，[TikTok达人运营团队](../下册-案例汇编/L-租赁与商务服务业/L01-TikTok达人运营AI协作.md#c-05-f01)在试点中，将筛选匹配、脚本辅助与履约状态提醒接起来，核心沟通和逾期事项由人接手；从合作确定到收样、创作、提交的平均周期由约一个月缩至约18天。

#### 核对总投入有没有转移

把同一范围内各岗位的准备、执行、交接、审核、返工和异常处理一起记录，再计入工具、系统及外部支持费用。前道节省与后道新增工作分别列出；交付数量不同时，按合格交付量比较单位投入。释放的工时、减少的现金支出和新增业务容量各有口径，不应直接互换。

> **案例小贴士｜一人主体也有外部协作投入。** [黄碧云](../下册-案例汇编/L-租赁与商务服务业/L02-黄碧云零售咨询的AI应用.md#s-32-f01)自述的一人咨询主体，也有付费的财务、短视频与开发伙伴。比较总投入时，应将这些费用和协作时间一并计入。

若初稿更快，但审核与更正增加，就应先修正输入、检查与分工，再决定是否扩大生成。

#### 回到阶段转化与业务结果

对销售，流程记录继续关联第二章确定的同批有效线索和商机，观察等待、需求遗漏、方案返工与商务障碍减少后，是否支持阶段转化及签约。短期可以先取得交接、周期和合格产物的记录，签约则按相应业务周期跟踪。扩大有效线索时，也要检查核实、分配和后续跟进能否承接，避免新增名单挤占已有商机推进。

根据观察结果决定下一步投入：瓶颈已经转移到下游时，调整相应环节；产物没有被采用时，先核实原因；业务条件尚未成立时，保留人工判断与必要等待。

<a id="section-3-4"></a>
## 3.4 本章小结

单点提升未必带来整体改善，因为工作还要经过下游承接：局部节省可能转为修补，新增产出可能挤进已有瓶颈，资料也可能因名称、版本、状态和访问条件而无法使用。改造需要从真实断点出发，让交接标准、容量、审核和异常处理相互配合，再观察完整交付。

这些措施最后落到组织上下文的贯通：依据与决定能够延续，当前状态能够辨认，变更能够到达使用者，责任与权限能够支持下一步。参与者据此继续工作，同时把本次结果交回相关记录。类似业务反复发生、多个流程同时运行后，还需让已完成的工作改善后续的依据、方法与分工。第四章继续分析怎样通过跨轮次复用和人机接力，在持续收益的前提下加快有效业务周转。
