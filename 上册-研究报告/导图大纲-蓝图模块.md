## 一、根节点：第五章 实施建议：从改造蓝图到共同基础设施

> 总命题：前面的分析从具体任务出发，沿着交接看到流程与组织。企业准备实施时，可以把顺序倒过来——先明确方向，形成业务与改造蓝图，再选择任务、确定边界，从一个能够验收的范围运行起来。
> 共同基础设施随实际工作补齐：任务与交接的约定让大家能够配合，能力网络让任务找到承接者，企业上下文与知识网络让执行和判断有依据。

## 三、二级与三级节点展开

### 3.1 主枝 5.1 — 从方向倒推改造蓝图

```
- 蓝图回答四层问题
  - 目标客户为什么选择我们
  - 企业需要提供什么业务与能力
  - 这些业务经过哪些工作流
  - 工作流中又有哪些任务、判断和交接
- 设计顺序倒推：方向 → 业务 → 工作流 → 任务
- 蓝图的内容表（6 行）
  - 客户与经营目标
  - 业务与职能
  - 工作流
  - 具体任务
  - 改造依赖
  - 基线与预期
- 蓝图不是一次性完备，而是足以发现关系
  - 改一个环节会影响谁
  - 某个目标是否需要先补资料
  - 某项工具是否只解决了表面问题
- 案例佐证
  - [C02] 非标制造企业AI报价：从直接出价退回分段协作
  - [C04] 压力容器企业：需求讨论中财务、采购、仓库提前
- 后续衔接：再用四象限筛选任务，边界才有业务依据
```

### 3.2 主枝 5.2 — 用四象限确定改造边界

```
- 四象限的判断维度
  - 纵向：是否应该交给AI参与改造（客户价值与企业取舍）
  - 横向：当前能否做好（输入、质量、工具条件、实测结果）
- 四象限矩阵（4 格）
  - 应该做 ∩ 能做好 → 优先候选
  - 应该做 ∩ 尚不能 → 准备与观察
  - 不应做 ∩ 能做好 → 保留现有机制
  - 不应做 ∩ 尚不能 → 暂不投入
- 边界确认原则
  - "尚不能"包括证据不足（先受控任务再调整）
  - 客户直接沟通与沟通准备应当拆开
  - 一芥取向：人主导、AI辅助；关系、承诺、判断由人承担
- 进入优先候选后的排序维度
  - 经营价值高
  - 负责人明确
  - 验收可做
  - 前置条件较齐
  - 下游能够接住
- 案例佐证
  - [I04] 运动门店SaaS：录音工牌未做，能采集不等于值得采集
```

### 3.3 主枝 5.3 — 从局部运行到逐步扩展

```
- 局部运行的选取标准
  - 能够看清输入、交付和责任的范围
  - 先确认一次任务可以完成
  - 再检查跨岗位接手
  - 之后在验证过的条件内引入定时或事件触发
- 每次扩展要说明新增工作与责任
- 案例佐证（局部与边界）
  - [F10] 上海消费品门店对账：试点控制在个位数门店
  - [C11] 澳洲乳企海外动销分析：先跑中国一条产品线
- 一次试验的记录表（6 行）
  - 原来的任务、质量和投入
  - 新安排与负责人
  - 采用及放弃原因
  - 合格交付、等待与返工
  - 人工介入、维护与费用
  - 业务结果与未验证事项
- 工具完成以后留出改进与停止空间
  - [F09] 3C外贸企业：30天大系统未达预期，强调同事能用、经常能用
  - [I04] 已有报表但调用很少，按真实采用复核投入
- 试点驱动的基建生长逻辑
  - 同一字段反复解释 → 补共同约定
  - 经常找不到可用工具 → 补能力目录
  - 依据散在不同设备 → 补知识发现机制
- 后续衔接：以下三项基建由实际需要生长
```

### 3.4 主枝 5.4 — 企业基建（一）：任务与交接的共同约定

```
- 共同约定的目的：让人和智能体理解同一件事
- 共同约定的内容表（6 行）
  - 业务对象与标识
  - 输入与依据
  - 产物与状态
  - 分工与责任
  - 交接与返回
  - 更新与生效
- 建设方式
  - 先为一条试点流程建立简短说明
  - 随着使用补齐例外
  - 不必把全部操作写成庞大手册
  - 重要边界不能只存在于某个人的记忆里
- 共同约定的维护机制
  - 执行员工与标准负责人共同参与
  - 约定进入实际任务以后要允许反馈回来
  - 反复出现的缺项 → 补输入要求
  - 误用的状态 → 改定义
  - 异常无人接手 → 责任没有落实
  - 改完还要检查下一次是否更可靠
- 案例佐证
  - [附A01] 工作切片与SOP共创：员工校准、主管审核
  - [F12] 交个朋友虚拟IP内容：人的概念需要先对齐
```

### 3.5 主枝 5.5 — 企业基建（二）：能力网络，让任务能够找到承接者

```
- 能力网络要解决的问题：任务分得清楚以后，还需要知道谁能做
- 企业常见的分散能力
  - 一位专业人员的判断
  - 一段规则程序
  - 一个内部工具
  - 某类智能体
  - 已经验证过的方法
- 能力登记表（6 行）
  - 名称、标识与维护人
  - 输入与产物
  - 适用范围
  - 质量与验收
  - 接入与使用方式
  - 投入与状态
- 能力调用与业务系统的连接
  - 任务针对哪个订单
  - 以谁的身份执行
  - 结果写到哪里
  - 沿共同约定落实
- 任务路由的演进
  - 先由人选择承接者
  - 规则明确、条件已验证的部分再逐步采用程序分发
  - 需要专业判断或新情况时回到相应负责人
- 能力网络的维护
  - 能力失效 → 更新登记
  - 版本改变 → 更新登记
  - 负责人调整 → 更新登记
- 案例佐证
  - [待04] 零一数科：已有业务工具，部门FDE连接仍属规划
- 与知识网络的关系
  - 能力网络回答"交给谁做"
  - 知识网络回答"依据什么做"
  - 两者通过任务连接：找到合适承接者 + 提供有效上下文 + 把结果与修正带回来
```

### 3.6 主枝 5.6 — 企业基建（三）：企业上下文和统一知识库

```
- 企业上下文的组成
  - 当前目标
  - 业务规则
  - 客户与项目状态
  - 历史决定
  - 任务经验
  - 适用方法
- 业务系统与知识建设的关系
  - 当前客户、任务与执行状态由业务系统维护
  - 知识建设关联这些事实
  - 明确每类内容的主要维护位置
- 风险提示：同一项目在任务系统、个人笔记、智能体记忆里各有一套状态
  → 新的工具反而会放大混乱
```

#### 3.6.1 主枝 5.7 — 把统一知识库理解为共同使用的知识网络

```
- 资料的现实分布
  - 手机上保存网页
  - 桌面上持续采集播客和视频
  - 项目工作区里有 PRD、Bug 与回归记录
  - 历史会话中保存着决定理由
- "统一"的重新定义：标识 + 索引 + 维护约定
- 重要知识按需同步，原始内容仍可留在原设备或系统
- 企业不必先把所有资料搬到同一处
- 混合式知识网络三层结构
  - 原始资料：网页/快照、音视频/转写、项目文件、会话、业务记录
  - 统一索引：资源标识、位置、类型、关联对象、更新、维护人、访问范围
  - 提炼后的知识：背景、决定、判断、案例、方法
- 原始资料与知识的不同作用
  - 文章被收录 → 可以查到
  - 判断被确认 → 负责人认可其适用范围
  - 检索到有出处的内容，还要判断是否足以支持当前任务
```

#### 3.6.2 主枝 5.8 — 资源注册、统一索引与跨节点查询

```
- 资源注册
  - 报备自己有哪些内容
  - 登记项：稳定标识、资料类型、来源位置、当前版本、关联项目或客户、维护人、访问范围
  - 原始资料变化时登记也要能更新
- 统一索引
  - 把登记按对象和主题关联
  - 先从关键词和全文发现做起
  - 有需要时再加入语义检索
  - 索引负责定位，原文负责提供依据
  - 二者分别维护，避免一份旧摘要长期替代已经更新的来源
- 跨节点查询
  - 先找到有权访问的资源
  - 再向来源取得正文或片段
  - 同时返回出处与版本
  - 节点离线、资料缺失或版本变化时把缺口带回任务
  - 执行者知道掌握了什么、还缺什么，才可能作出可靠判断
- 知识网络流程图（mermaid）
  - 资料 → 资源注册 → 统一索引
  - 当前任务 → 统一索引
  - 统一索引 → 按访问范围取回来源 → 组织有效上下文
  - 有效上下文 → 执行、判断与交接 → 结果、修正与候选知识
  - 确认并维护知识 → 统一索引（闭环）
```

#### 3.6.3 主枝 5.9 — 资料怎样沉淀为下一次可用的知识

```
- 三种状态的区分
  - 已收录资料：解决发现
  - 候选知识：提出值得保留的认识
  - 已确认知识：落实业务共识、方法和适用范围
- 任务前后流程
  - 任务开始前先查已有知识，避免重复写同样结论
  - 任务结束后留下结果、修正和来源
  - 再决定新增、合并或更新
  - 重要决定保留当时为什么这样选
- 知识的维护项（4 行）
  - 名称与关联对象
  - 结论、依据与适用范围
  - 状态、确认人及日期
  - 版本、复核与替代关系
- 维护动作的触发条件
  - PRD 更新
  - 业务规则改变
  - 原始证据被修正
- 维护动作
  - 相关知识进入复核
  - 旧版本保留历史
  - 不继续作为默认依据
- 区分"过去讨论过"与"现在可以采用"
- 工具与能力
  - Notion、Obsidian 等可作为知识编辑入口
  - 组织上下文智能体：发现、读取、整理相关资料；可由多个能力共同完成
  - 业务负责人仍需确认重要知识与判断
- 一芥的建设思路（编者讨论）
  - DreamMate 中 dreammate-node：节点与能力接入思路
  - session-reader：历史会话查找与读取
  - 提炼与确认后的知识另行维护
  - 具体接入与完整实现仍需验证
```

#### 3.6.4 主枝 5.10 — 用一次跨来源任务验收知识网络

```
- 验收任务的选择：产品改进任务
  - 手机上收录过相关文章
  - 桌面有相关播客与视频
  - 项目里有 PRD 和 Bug
  - 历史会话保留了为什么没有采用某方案
  - 任务：把这些来源组织到一起，形成能够追溯的建议
  - 由负责人决定是否采纳
- 验收维度（5 个）
  - 是否找到相关依据
  - 是否读到了正确版本
  - 访问范围是否恰当
  - 缺失是否明确
  - 建议是否减少了重复解释和引用过时结论
- 验收的最终落点
  - 知识网络的价值最后还要回到任务
  - 它是否实际帮助下一次工作更可靠地完成
- 总结：先从一个值得改造、能够验收的范围开始
  - 在运行中形成共同约定
  - 连接能力
  - 积累有效知识
  - 再按结果逐步扩展
```

## 四、关键概念与全文对照（速查）

```
- 总命题
  - 智力成为可调用的服务
  - 使更小的工作获得新的执行承接者
  - 企业有机会把任务、交接、验收和责任管理得更精细
  - 再把这种能力用于减少浪费、改善客户交付（精益经营）
- 与第一章的衔接
  - 技术变化推导精细化管理与精益经营（1.5）
- 与第三章的衔接
  - 上下文怎样随任务进入下一环节（3.3）
- 与第四章的衔接
  - 持续组织循环、组织智力循环、智力飞轮（4.2）
- 第三章番外 OPC／OPT（3.2 旁注）
  - 一人公司、一人团队：可能长期存在的过渡形态
  - 与本章"局部运行"互为参照
- 一芥采用的实施取向
  - 人主导、AI辅助
  - 客户直接沟通由人主导，AI做好准备与辅助
- 工作含义区分（避免混用）
  - 精细化管理：工作安排能力
  - 精益经营：减少无效投入、使资源服务客户价值
  - 持续组织循环：交付以后继续监测，按条件再次发起
  - 组织智力循环：反馈实际改变后续规则、上下文、方法或分工
  - 智力飞轮：上述改变在同口径结果中形成持续改善
```
