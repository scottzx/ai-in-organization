每个人都能更快完成自己的任务以后，企业会遇到一种新的不协调：文件更多，交付却未必更快；前道产出增加，后道反而排起了队。一名员工认为已经完成的东西，另一名员工可能仍需重新解释、检查或制作。

任务化管理因此还需要走出个人。跨岗位工作流关注的是，一次工作怎样进入下一个人的责任范围，以及对方能否据此继续推进。共同语言、有效上下文和验收安排，决定单点提效能够传递多远。

<a id="section-3-1"></a>
## 3.1 为什么各自提效，整条工作流仍然会卡住

一种摩擦来自职责不清。员工能用AI制作更多产物，却没有人说明谁负责确认、谁接手异常、谁维护工具。于是，有的任务重复做，有的任务停在“已生成”，还有的异常始终无人跟进。

另一种摩擦来自采用差异。一个熟练使用AI的人可以很快完成初稿，接手的人却未必理解其中依据，也未必愿意使用同样工具。前者以为工作已经交出，后者还在重复查找和确认。工具能力与人员采用并不总按同一速度变化。

还有一种摩擦来自上下文丢失。上游留下最终文件，却没有交出商品原图、客户约束、判断理由和未解决问题。下游只好重新解释任务，甚至重复一次已经完成的调查。交付物存在，能够继续工作的依据却不完整。

可以用一个假设理解审核环节：若每名员工的产量都提高十倍，负责人仍逐份审核，进入审核的数量就可能大幅增加。若产物还新增了真实性等核验要求，每份审核也可能更费力。这里的十倍是机制示例，不能当作已测效果。

森马电商的材料提供了实际观察：商品图生成以后，员工仍要修正领标，检查面料、版型和细节，受访者也承认出现了额外工作。它说明核验内容发生变化，净审核工时还没有充分测量。[完整案例F02][F02]

因此，研究整条工作流要看最终通过验收的交付、等待和返工。生成数量值得记录，已经能够被下一环节使用的数量更能说明流程是否改善。

<a id="sidebar-opc-opt"></a>
## 番外小贴士｜一人公司、一人团队：可能长期存在的过渡形态

本节用OPC指一人公司，用OPT指一人团队，讨论一个人借助AI跨职能承接工作的安排。**我们的判断是，这是一种可能长期存在的过渡形态。**“过渡”指工具能力、人的学习采用和组织协作尚未对齐时的安排，不设必然消失的期限，也不把它当作所有企业的共同终局。

当下，一个熟练使用AI的人，有时确实比现有多人接力更快。原因可能很实际：产物只需要满足当前阶段要求，而协调另一位同事，需要解释背景、约时间、等待和反复确认。一个人用AI先做出够用的结果，就能让事情往前走。

我们编者原从事解决方案工程，没有专门的产品原型设计能力。现在，形成解决方案以后，可以直接借助AI制作原型，和客户确认大体模块、方向与产品边界。过去需要协调产品或设计人员的一段制作，可以先由我们与AI完成。这是编者在需求沟通阶段的自述，没有独立计时或第三方效果验证。

原型进入细化设计和工程实现以后，仍要处理完整交互、异常与实现约束。能让AI生成代码或修复报错的人，也需要判断修复是否正确、有没有遗漏、是否存在更合适的方案。执行范围扩大以后，判断产物好坏、引导下一步的能力仍然稀缺。

亚当·斯密在《国富论》第一篇第一章讨论了分工通过熟练程度、减少工作切换和机器改进提高生产率的机制。这为重新比较专业化收益与协作投入提供了历史参照，却不能直接证明AI时代的某种组织形态必然出现或消失。[分工论述原文](https://www.adamsmithworks.org/documents/book-i)

人的时间、精力和专业长板有限，熟练使用AI也不会自动产生所有领域的验收能力。与此同时，不同人学习工具、组织调整边界的速度不同，技术也会继续变化。一人跨职能的安排因此可能长期与其他形态共存：有些任务适合直接完成，有些任务仍需要更深的专业判断与更多交付能力。

专业分工可以通过新的任务接口、共享上下文或外部伙伴实现，具体岗位由实际工作决定。下册[L02 黄碧云零售咨询的AI应用][L02]还提醒我们，一人主体背后可能存在付费财务、内容和开发伙伴。人数少，不意味着所有劳动都由一个人完成。

所以，接下来的问题是：当工作需要跨人、跨岗位继续推进时，怎样减少重复解释、标准不一与上下文丢失，让专业判断与AI执行能够接起来？

<a id="section-3-3"></a>
## 3.2 统一任务语言与交接颗粒度

每个人内部怎样拆工作，可以保留差异。组织需要共同确认的，是进入协作边界时交出什么、各字段表示什么、什么状态代表能够继续推进。

以订单为例，“已完成”可能指销售已经成交，也可能指配置确认、装配完成或已经发货。若几个岗位使用同一个词表示不同进度，工具再快也会把错误传下去。任务语言要围绕业务对象，明确每个状态和它对应的责任。

在[C06 电助力单车企业][C06]中，订单进入工作流、整理成结构化记录，再由装配人员配车。交接的关键是配置信息能够被正确使用。企业应围绕这个边界确认需要哪些字段、缺项怎样返回，以及谁判断配车依据足够；现有材料没有披露的具体制度，仍需继续了解。

[F12 交个朋友虚拟IP内容生产][F12]呈现的是另一类共同语言：AI为镜头打标签后，编导先讨论人的概念是否一致，再把规则交回工具重新标注。团队统一“这个标签是什么意思”，是重复生产成立之前的工作。

[J01 基金公司AI研发培训][J01]则把真实需求、产品、业务和研发放到一起，共创Spec文档。它说明共同上下文需要有人参与确认。培训已发生，后续版本与评审怎样维护，还需要长期工作记录。

这些做法都不能直接拼成所有企业通用的一套制度。它们共同提出了一个问题：下一环节需要哪些最少而足够的信息？共同颗粒度可以围绕这个问题确定，无须把所有任务强行拆成一样大小。

<a id="section-3-4"></a>
## 3.3 上下文怎样随任务进入下一环节

一份结果文件通常只是交接的一部分。下一位承接者还需要知道来源、业务约束、已经作出的决定、当前版本和未解决问题。

例如，供应商规格书可以先由AI分析，再形成交互原型供人讨论。原型被确认以后，进入实现环节的人仍需要找到原规格、确认过的要求，以及哪些假设尚未验证。只有原型链接，未必足以支持后续专业工作。[单车企业规格沟通过程C06][C06]

商品图片也类似。审核者需要真实商品依据、允许修改的范围和图片用途，才能判断生成结果是否可用。若只交一批图片，让审核者重新猜测要求，前道节省的一部分时间就可能变成下游投入。

企业可以围绕订单、商品、客户、报价或项目建立共同资料入口。关键是同一对象的记录能够对应，不同岗位能够获得需要的范围，变化以后能找到当前版本。个人聊天记录可以保留过程，但组织还要明确哪些内容已确认、哪些仍是候选、谁负责更新。

| 交接内容 | 它帮助下一环节解决什么 |
| --- | --- |
| 产物与业务对象 | 这是哪项工作、为哪个客户或订单服务 |
| 来源与版本 | 依据是否可查，是否仍适用 |
| 约束与判断理由 | 为什么这样做，哪些边界不能越过 |
| 待核问题 | 哪些尚未解决，谁继续处理 |
| 验收与下一责任人 | 怎样确认可接手，之后由谁推进 |

这一安排减少的是为继续工作而重复取得依据的劳动。第五章还会进一步讨论，分散在设备、系统与智能体里的资料，怎样通过共同知识网络被发现和使用。

<a id="section-3-5"></a>
## 3.4 把交接、验收和异常返回放进流程

交接标准要能够影响动作。资料不全时能否继续？预检未通过时返回谁？规则算不出结果时谁判断？这些安排要在工作到达边界以前明确。

[C02 非标制造企业AI报价][C02]是一个具体转折。团队最初希望模型理解图纸后直接出价，结果经常对不上真实成本，后来改为模型提取材料、尺寸和结构，再进入企业自己的物料、供应商和规则库，每单由人校准以后对外输出。模型、规则与专业判断的边界因此被重新安排。

这里的人工校准并不是生成之后随便看一眼。对外报价涉及企业能否制造、成本怎样形成等依据，验收需要落到这些业务条件。来源称相关工作量减少，并提到工作安排和KPI调整，尚没有新增订单与利润的完整证据。

[待03 消费品包装预检][待03]把验收中的一部分往前放：设计提交后先做预检，处理能够发现的低级问题，再交专业人员判断。这提出了减少后道返工的机制，实际漏审、返工与总周期改善仍待测量。

[S01 浙江车管所AI网办审核][S01]则把图片识别接到了既有系统操作。正常业务继续流转，异常交人处理。技术让过去人工放宽的审核尺度变得显性以后，采用哪种尺度仍由业务管理方确认。识别、程序执行与业务规则，各有自己的责任。

预检、抽查和逐项复核适合不同质量要求，不能从某个案例推成固定比例。选择何种方式，需要同时看错误后果、发现能力、核验投入和最终交付。

<a id="section-3-6"></a>
## 3.5 重新明确职能：从谁使用AI到谁对哪段结果负责

工具账号属于谁，不能充分说明一段工作的责任。一个任务可能由业务人员发起、AI处理、程序写入、另一位专业人员验收。执行者与结果责任人可以不同，但不能缺位。

至少有几种责任需要辨认：确定业务标准，提供有效依据，执行任务，判断产物，处理异常，以及维护流程和工具。小团队可能由同一人兼任，大团队可能需要分工。岗位名称是否调整，应由这些实际工作决定。

OPC／OPT的讨论已经说明，一个人加AI可能在局部任务更快。当质量要求提高、工作需要更多专业能力时，重新建立有效协作仍然重要。减少协作摩擦，可以让专业分工继续发挥价值。

[C05 制造企业订单与岗位权限调整][C05]虽然没有清楚展示模型任务，却提供了一段很有用的职责材料：车间可按工况调整部分数量或尺寸，价格由下单端控制，办公室还需要相应价格完成核对。共享同一订单，不等于每个人能够看和改同样的内容。

职能边界还包括谁能修改共同标准、修改后如何生效，以及出了问题谁接手。若大家都认为工具会自动完成，实际无人维护，工作就会在边界上停住。

<a id="section-3-7"></a>
## 3.6 用完整交付检查单点提效有没有传下去

流程验证可以沿着同一业务对象走一遍：从输入进入，到各段执行、交接与验收，再到最终使用。记录等待在哪里发生，返工为何发生，以及原来省下的劳动是否转移到了别人身上。

[L01 TikTok达人运营AI协作][L01]提供了一项流程指标：来源称试运行中，从合作确定到收样、创作和提交，平均周期由约一个月缩到约18天。这个口径比单次筛选更接近完整工作链，但样本与总投入未披露，也没有直接证明GMV或利润增长。

同样，车管所审核提速仍不能代替群众最终拿到材料的总时长；包装预检发现问题仍不能代替最终上线；订单整理完成仍不能代替正确装配。每条线都要说明，当前效果走到了哪个边界。

当多项任务已经能够可靠接起来，企业才更有条件考虑定时发起、事件触发和跨流程分发。下一章将讨论这种组织运行的可能性，同时区分现有局部实践与尚待验证的目标。
