管理讨论常从岗位开始：销售怎样用AI，设计师怎样用AI，程序员怎样用AI。真正改变工作安排时，还需要再往下走一步。一名销售既准备资料，也判断需求、沟通、报价和跟进；一名工程师既编码，也理解需求、检查、测试和维护。这些任务的输入、产物和判断方式不同，适合采用的执行方式也不同。

岗位工作任务化，就是把这些差别说清，使一小段工作能够被分配、执行、交接和验收。岗位仍可以保留，人的专业判断与责任也可以保留；发生变化的是工作怎样被承接。

<a id="section-2-1"></a>
## 2.1 从岗位职责表到每天实际完成的任务

“负责招聘”是一项职责，却不足以直接交给执行者。一次招聘可能先要理解客户岗位，再研究哪些公司有合适人才，寻找候选、确认意向，最后由顾问沟通和推进。把这些工作拆开，才能讨论其中哪一段可以获得新的承接者。

下册[L05 CGL招聘AI协作][L05]展示了一条前道流程：顾问提供岗位需求，工具参与人才地图、简历筛选和意向确认，再把感兴趣的候选人交给顾问。变化落在具体工作，而不只是给招聘顾问增加一个聊天账号。

组织需要的任务说明，应当能够让下一位承接者知道从哪里开始、交出什么。它可以很简短，但要包含实际对象。例如，“整理客户资料”可以进一步说明为：围绕本次拜访，把已确认需求、历史沟通和待核问题整理在同一份准备材料中，供负责人决定会谈重点。

这样的说明也帮助判断任务是否值得拆。若解释所需的时间已经超过实际执行，或者输出仍需要另一个人从头重做，企业就要重新划分边界，而不是继续追求更细的拆分。

<a id="section-2-2"></a>
## 2.2 任务怎样拆：围绕产物与判断划分边界

本书建议用六个问题说明一次任务：为什么做，依据什么，交出什么，怎样判断完成，由什么执行，以及由谁对结果负责。它们把“让AI帮一下”转成能够讨论的工作安排。

以自媒体选题为说明性例子：人先确定关注的受众与方向，AI搜集相关资料并保留出处，人再判断题目是否符合定位、是否有足够依据。如果判断未通过，下一步可以是补资料、改角度或停止。搜索与选择有了不同承担者，但整个选题仍由人负责。

同一项工作在不同阶段，可以采用不同分工。原型阶段关注是否把需求讲清；工程阶段需要处理完整交互、异常、测试与运行。一次原型足够支持客户讨论，并不代表已经足够承担生产交付。

| 要说明的内容 | 选题任务的示例 |
| --- | --- |
| 目标 | 为本次内容讨论准备有依据的候选题 |
| 输入与上下文 | 受众、定位、历史内容、已有资料与本次约束 |
| 产物 | 候选题、事实依据、来源与待核问题 |
| 验收 | 方向符合、依据可查、关键不确定性清楚 |
| 执行 | 人提出要求，AI检索整理，人作判断 |
| 结果责任 | 选题负责人确认采用、补充或停止 |

这张表是实施示例，不是新增案例效果。企业可以按实际任务简化字段，关键在于承接者能够工作，判断者能够确认结果。

<a id="section-2-3"></a>
## 2.3 信息准备类岗位：从搜索整理转向判断与接手

招聘前道的信息准备更快以后，顾问需要接住更多候选资料。CGL材料中一次演示出现了1808人、匹配388人、沟通323人、意向19人的数字。它们属于该次过程，不能换算成公司的平均转化率，也没有说明后续全部完成了招聘交付。任务拆解让前道变化更清楚，也使我们能够继续追问顾问的承接能力与候选质量。

类似关系出现在[Q01 药师AI助手试用][Q01]。专业人员面对患者交流，工具参与记录、归档、检索与文书整理。它有机会减少服务中分心查找的动作，药师仍承担专业沟通和判断。受访者提到医院拿到设备及试用的范围，但设备发放不能代替持续采用，更不能代替服务质量证据。

销售准备也可以拆到这一层。[I05 AI员工服务商的教育销售交接实践][I05]中，供应商描述了试听期间的信息整理、意向标签和电话前的沟通提示，销售再接手。来源还包含自动初步沟通的做法，应按第三方实际描述记录；一芥的实施取向则是客户直接沟通由人主导，AI做好准备与辅助。

这些岗位的共同变化，是让资料准备与后续专业服务形成明确交接。准备材料是否准确、是否能追到原始记录、是否帮助人判断，比分发了多少摘要更接近任务质量。

<a id="section-2-4"></a>
## 2.4 内容、设计与开发岗位：执行方式改变以后，人判断什么

内容生产往往最容易出现明显的单点提速。森马电商材料中，商品图、换色和短视频等已有工具参与，员工仍要修正错误领标、检查面料、版型和细节。这说明制作与商品一致性确认属于不同任务。材料支持审核内容发生变化，净审核工时究竟增加还是减少，还需要实测。[完整案例F02][F02]

[F04 女装直播企业][F04]则描述了先形成视觉需求、制作图片、测试流量，再决定做货的方式。AI在这里还可能改变投入顺序，让部分实物制作发生在较后阶段。是否真的减少了库存或改善利润，仍需相关数据；不能只用图片制作时间宣布全部开发过程得到同样改善。

内容创作还有判断依据怎样保留的问题。在[C06 电助力单车企业][C06]中，员工记录老板的修改意见，再整理成后续创作规范。一次作品的审核意见减少，是局部线索；更值得研究的是明确的判断如何进入下一次任务，让创作者少从头猜测要求。

代码工作同样需要拆开。[C07 制造企业AI辅助研发试点][C07]保留了三个小组、几天内的短期反馈：编码时间约省三分之一，文档省一半多，测试基本持平。不能把这几个数字合成总研发节时，更不能据测试持平断言已经形成测试瓶颈。它提示我们继续追踪需求、复核、测试、发布和维护。

[待05 小裂变][待05]的内部过程体现了另一种交接：老板先做原型，研发再接手构建完整产品。AI扩大业务人员能够直接执行的范围，专业团队仍负责把原型推进到可持续使用的系统。判断原型好不好，与判断系统能否可靠交付，需要的经验并不完全相同。

<a id="section-2-5"></a>
## 2.5 财务与专业服务岗位：让执行单元适配工作性质

任务拆细以后，还可以避免把不同性质的工作交给同一种工具。

[F10 上海消费品门店AI对账][F10]中，OCR和视觉能力参与首轮读取与核对，员工继续追查真正差异。来源称部分门店每个结算周期由一两个人天缩到几个小时，也发现了约1—3个百分点账目差异。差异包含少收与多收，尚未披露净值和到账，因此不能写成收入或利润增长。

对账的管理目标要继续走到差异确认和处理。机器发现了一条不一致，意味着有了待查事项；对方是否认可、是否修正、钱是否到账，是后面的任务。把前道发现与最终结果分开，才不会把问题清单当作已实现收益。

[待03 消费品企业包装AI预检][待03]进一步显示模型、程序和人的差别。文字与图像可以分模块处理，固定的热量等计算交给代码，模型参与解释与补录建议，复杂专业表达仍由人判断。适配工作性质，比让同一模型包办整张包装更有利于检查。

在[L07 AI法务服务与专业复核][L07]中，工具可以追问背景、整理初稿，专业团队继续校验和维护。购买工具与购买包含专业团队的服务，交付范围不同。生成了一份文书，只完成了其中一段工作；客户的问题是否得到解决，需要后续服务和专业责任共同支撑。

这些案例帮助我们把“AI替代了谁”改成更具体的问题：资料整理由什么完成，确定计算由什么完成，专业判断在哪里发生，谁确认可以对外使用。

<a id="section-2-6"></a>
## 2.6 从个人一次尝试到可复用的任务方法

员工偶然做成一次，并不意味着其他人可以直接复制。方法要复用，先要确认记录的是实际工作，输入条件和判断要求没有被省略。

[附A01 工作切片与SOP共创方法][附A01]介绍了一条校准过程：把工作记录细到单次任务，AI整理为图文SOP，先交执行员工确认，再由主管审核。之后比较多人做法，才决定哪些部分适合自动化、AI或继续由人承担。这是方法与实践者自述，具体客户尚未可靠识别，也没有长期改善数据。

两次校准分别承担不同责任。员工能够发现记录是否漏掉真实操作，主管需要判断哪些做法值得成为共同标准。如果省去这两步，把一次整理直接发布为规则，原有误差也可能被固定下来。

[待04 零一数科AI应用][待04]中的业务负责人制作工具、承担整段流程，是方法逐步进入工作的一种线索。已经使用的工具与规划中的部门FDE连接，需要分别表述。内部有几个好工具，距离组织中的任务都能找到承接者，仍有系统连接、共同标准和维护责任要补齐。

可复用方法可以表现为工作说明、模板、固定工作流或技能。具体形式由任务决定。企业首先应确认它在真实条件下能重复完成，再决定怎样推广，以及由谁维护变化。

<a id="section-2-7"></a>
## 2.7 任务层面怎样判断提效

单点效率值得记录，但比较对象应当是一项达到同一质量要求的任务。准备和执行省下的时间，需要与核验、修改、失败重做及维护一起观察。

例如，过去一个人独立完成资料整理，现在由AI先做、负责人检查。若检查很快并能发现问题，任务总投入可能降低；若负责人必须重新搜集全部资料，生成速度就没有说明真正节省。这里需要的是实际工作记录，而不是从服务响应时间推算人工价值。

| 观察项 | 需要记录什么 |
| --- | --- |
| 采用 | 计划使用的人是否实际使用，什么条件下放弃 |
| 合格产物 | 产物能否达到既定标准并用于下一步 |
| 总投入 | 准备、执行、核验、返工、维护和服务费用 |
| 下游影响 | 是否减少等待，是否把新增工作交给别人 |
| 业务关联 | 释放的能力用于什么，是否改善客户交付 |

一个岗位内部把任务分清以后，往往很快就能看到执行方式的改变。接下来，企业会遇到另一个问题：每个人按自己的理解拆出的任务，怎样在组织里接起来？这要求共同语言、上下文和交接标准，第三章将沿着完整工作流继续展开。
