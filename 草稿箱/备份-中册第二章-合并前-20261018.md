# 第二章　建设实施：从企业现状到可验证的业务结果

一芥智能研究院｜《企业数智化转型研究报告》中册｜初稿 v0.2｜2026年10月18日

[中册目录](../中册-行业解决方案/README.md) · [上一章](备份-中册第一章-合并前-20261018.md) · [下册企业案例](../下册-案例汇编/README.md)

行业方案提供原架构和可选模块，企业实施需要回答的是：当前怎样工作，准备改善什么，改进后的业务怎样运行，为此需要建成哪些能力、投入哪些资源。本章按**摸清现状、确认目标、画出蓝图、制定计划**展开，再进入建设、运行、验收和反馈。每一步形成下一步能够使用的依据；建设中发现原判断不成立时，回到相应步骤修订，并保留变更记录。

数字化方案本身包含数据、模型、应用、设备与连接等建设。已有基础的企业核实实际使用，复用有效部分并补足缺口；基础较薄的企业从选定业务范围建起。智力服务可以协助需求、开发和测试，使部分局部建设更容易开展，网络连接和分析任务也可以同步设计。三化按业务依赖组合，具体次序由本企业条件决定。

## 2.1 摸清现状，确认本轮目标

<a id="section-2-1-1"></a>
### 摸清现状：形成企业实际基线

先了解本企业的产品或服务、客户与交付方式，画出现行主要工作及上下游关系，明确本次摸底覆盖哪些组织、产品和场所。再选择能够追踪的一类工作，如设计变更、订单执行、质量处置或设备维修，取得正常完成、发生异常和仍未结束的代表性记录。执行者说明收到什么、怎样处理、交出什么，接收者核对取得的产物能否继续使用。沿同一业务对象记录发生时间、处理和等待、补问和返工，现场操作与系统记录相互核实。

摸底还要追到支撑这些工作的资源。业务人员与技术人员共同列出现有系统、设备、表格、数据、模型、专业工具和外部伙伴，核对哪些正在使用、覆盖什么范围、由谁维护。系统有某项功能，还需看本企业是否配置、输入是否可靠、结果是否实际采用。Excel已经包含数字记录，复杂系统也可能留下口径、版本和交接缺口，企业规模和软件数量只说明部分条件。

例如，查看一笔签约后尚未排产的订单，要核实合同启动条件、产品准备、物料、质量状态和产能，再判断是否已经偏离约定。订单、工单与生产批次能否对应，相关人员能否取得当前资料，异常由谁协调，都会影响判断。资料缺失、尚未确认和已经确认未完成分别记录；若实际缺少物料，继续核查采购与供应条件，若资料已经存在却未传到计划人员，则查明连接与接手位置。

把核实结果放回适用的行业原架构，形成模块对照：原方案要求什么，企业已有能力能做什么，实际工作在哪里受阻。原因需要有记录支持，访谈解释先作为待验证判断。仪表测量与模型不适用、数据无法关联、流程没有接手、人员资源不足，分别对应不同的改进办法。

这一步交付**企业现状与差距记录**，包括实际业务流程、对象与产物关系、资源及采用清单、基线数据、已核实差距和待确认事项。业务、技术及接收方共同核对，缺少依据的事项落实补查责任。后续目标和预算从这份记录出发。

<a id="section-2-1-2"></a>
### 确认目标：说明希望达到的业务状态

现状中的差距需要先判断业务价值。业务负责人说明哪些问题影响客户、交付、质量、资源或资金，接收方说明怎样的产物才足以继续工作，管理者核对人员与资源能否承接。建设对象据此确定，目标写到改进后的工作表现。

继续以订单执行为设计示例：若已确认启动条件满足的订单仍长期等待，本轮目标可以是及时识别受阻环节，形成经过确认并进入执行的安排。需要分别观察依据是否可靠、责任人是否接手、等待是否减少以及交期是否改善。若主要约束是设备能力或供应短缺，方案应包括相应业务措施，资料查询与分析只能承担其中适合的工作。

目标说明固定对象、起止点、质量要求、观察期、截止日和记录责任人，并明确本轮覆盖哪些客户、产品线或任务。目标值由企业基线、业务要求和可用资源确定；缺少基线时，先安排测量，不预填统一提升比例。新增数量进入后，判断与下游接收能力也需要有安排。

[压力容器企业](../下册-案例汇编/C-制造业/C04-压力容器企业成本核算需求梳理.md#s-05-f01)在需求讨论中要求提前处理财务、采购与仓库，因为每台设备的实际成本不清会影响下一轮报价。来源记录的是需求与设想阶段的需求核对和顺序调整，成本核算尚未交付。企业最迫切的成本依据由此进入了本轮目标与建设范围。

确认目标时，分别判断值得做与当前能否做好。有业务价值且已有可靠条件的，进入方案设计；价值明确但条件不足的，列出补建或验证范围；完整投入与价值不相称的，记录暂缓理由。有效的规则程序、专业软件和人工专业工作可以继续承担原任务。

这一步交付**经确认的目标与范围说明**，把每个目标关联到现状差距、接收标准、观察口径和负责人，并保留投入约束与优先次序。目标有了共同依据，才能判断蓝图中的建设是否必要。

<a id="section-2-2"></a>
## 2.2 画出蓝图，制定实施计划

<a id="section-2-2-1"></a>
### 画出蓝图：从目标倒推建设内容

蓝图描述改进后的业务怎样完成，以及支撑它运行的能力怎样组成。业务负责人先把目标状态画成工作接续：谁收到什么，完成哪些动作，交出什么，在哪里判断、批准和接手。再沿适用的原行业模块，确定数据、工具、应用、设备及服务的建设，说明现有部分怎样复用、缺少部分怎样补齐。

| 蓝图内容 | 需要设计到什么程度 |
| --- | --- |
| 业务与原模块 | 目标状态下的业务流程、产物和接收要求，对应原文件、模块名、编号及范围；保留、调整和新增内容分别标明。 |
| 数据、模型与工具 | 对象、字段、标识、状态、来源和版本关系，以及记录、查询、计算、仿真或控制所需的规则、知识模型、软件及验证方法。 |
| 系统、设备、人与伙伴连接 | 数据由何处维护、如何采集与传递，系统和设备怎样接入，人员及外部伙伴怎样接手；明确访问、写回、更新频率与异常处理。 |
| 智能任务与责任权限 | 任务如何触发、使用什么依据与工具、交出什么，由谁核验；哪些动作获准执行、哪些先批准，失败与超出范围交给谁。 |
| 目标状态与建设范围 | 每项目标由哪些功能和协作支持，形成哪些应用、数据、接口、设备配置及服务成果，如何验证可用与采用，本轮与后续范围怎样划分。 |

以订单受阻处置为蓝图示例，需要先把合同、订单、工单、采购与库存、质量状态对应起来，明确哪些关系是一对多、怎样处理变更。可以据此设计订单执行查询与异常处置应用，提供当前状态、有效来源、未决项和接手任务。已有系统维护的重要状态继续由原位置管理，接口或获准查询取得所需信息；缺少有效记录的环节，设计相应录入、采集和确认功能。

在这些条件上，智力服务可以整理跨职能背景、解释约束和准备处置建议，确定的状态核对与计算由适用程序执行。确需优化排程时，设计专业求解工具及模型验证，服务整理其输入和解释结果；有权人员确认影响与取舍，再使获准调整进入原计划及执行位置。界面能够展示状态、建议能够生成和生产安排实际生效，分别对应不同的建设与验收。

已有基础企业先核实现有模块的功能、数据与模型适用性、接口和维护条件，保留有效建设，补足当前目标所需的关系、连接和任务。基础薄弱企业则需要真正建成必要的数据模型、记录与计算工具、业务应用和现场条件。可选轻量表单、现有服务或小模块起步，智力服务协助需求、代码、适配和测试；成果仍需完成部署、专业核验与维护交接。缺少的设备、测量和控制能力也进入建设范围。

因此，方案既要写服务怎样参与，也要交代数字化方案本身怎样落地。AI参与建造的普通程序，运行时可以按固定规则完成任务；运行时调用模型的服务，另行明确输入、权限和质量要求。两类建设分别估算开发、调用与维护投入。

这一步交付**蓝图设计包**：业务流程与原模块对照、数据及模型设计、功能或应用原型、连接与接口设计、服务任务规格、责任权限和验收清单。使用方确认目标状态及采用方式，建设与维护方确认实现条件。蓝图中的设计成果进入项目计划，建设完成后再以部署、联调和运行记录确认实际交付。

<a id="section-2-2-2"></a>
### 制定计划：把蓝图拆成可交付的项目包

蓝图确定建什么，计划落实由谁、何时、按什么依赖把它建成。项目负责人将成果拆成可以交接和验收的项目包，给每包注明输入、产物、负责人及协作方、前置条件、工作量与预算依据、完成节点、验收人，以及试运行和维护安排。整体范围、共用资源和关键依赖在同一计划中核对。

下表是前述订单方案的项目包示例，具体名称和范围随企业条件调整。

| 项目包 | 主要产物 | 依赖与责任、验收 |
| --- | --- | --- |
| 业务与数据确认 | 订单及相关对象定义、状态规则、字段与来源映射、可验证样本。 | 业务和数据负责人依据现状与目标确认；专业人员核实工艺、质量等条件。 |
| 基础模块与工具建设 | 必要的采集或录入、数据表、查询计算、业务应用，以及配置或代码、测试记录。 | 建造者按蓝图实施，现场工作由相应专业人员承担；使用方验证真实对象与处理结果。 |
| 连接与协作实现 | 系统设备接口、同步任务、共同标识、权限、接手与失败恢复配置。 | 数据定义与来源权限确认后联调，原系统维护方及伙伴参与；验收读取、传递、写回和实际接手。 |
| 智能任务与处置验证 | 背景整理、约束分析及获准工具调用的可运行服务、测试和核验记录。 | 有效样本与工具可用后验证；业务判断者确认产物，重要动作由有权者批准。 |
| 试运行与维护移交 | 部署版本、实际采用、未完事项、操作培训、维护与恢复说明。 | 集成和专业验证完成后进入真实业务；使用方与维护方共同接收，约定后续复核。 |

每个项目包的预算分别列建设与运行支出，保留数量、单价或人时、期间与估算依据。采购和外部服务取得适配与报价依据，自建安排需求、开发、审查和返工时间，试运行安排业务人员与维护资源。共用采集、接口和培训统一归集；尚待验证的费用落实测量责任与决策节点，再据此批准投入。

计划按真实依赖安排并行和先后。对象与状态定义可以先于写回联调，获准读取已有数据时可以同步制作查询、整理服务和测试样本；现场缺少必要测量时，真实运行要等采集与专业验证完成。数字化、网络化、智能化的工作可以分布在多个项目包中共同推进，无须排成全企业先数字化、再联网、最后智能化的三轮工程。

[上海消费品门店](../下册-案例汇编/F-批发与零售业/F10-上海消费品门店AI对账.md#c-10-f01)据实施者自述，在多个候选任务中先选择较容易观察人工投入与差异的对账，试点控制在个位数门店，阶段为局部使用。节时记录继续与差异处理及实际到账相接，才能判断完整收益。范围、观察办法与后续处理需要共同进入计划。

这一步交付**可执行的项目计划与预算**，覆盖项目包、里程碑、依赖、责任、验收和试运行维护。启动后以实际完成和条件变化更新计划；接口无法取得、模型不适用或承接能力不足时，修订对应蓝图与范围，再确认新的安排。

<a id="section-2-3"></a>
## 2.3 完成建设、集成与真实运行

建设按项目包交出可以运行的成果。复用时核对版本、接口与使用条件，采购配置用真实业务验证适配，自建按已确认的规则、数据模型和验收样本开发。数据表需要接入首批有效数据，知识索引需要能够找到适用依据，应用需要在规定环境中部署，接口与服务需要完成调用及交接；设计文档与原型随之转成已建成的功能和工作方式。

先在测试环境验证查询、计算、模型调用、传递和写回，再按授权进入选定范围。正常输入之外，测试缺失、冲突、重复请求、版本变化、工具失败、超出权限与恢复。仿真、优化、控制及现场设备按专业要求核验，服务生成的说明与专业工具结果分别检查。用AI辅助生成的程序和测试方案同样接受工程审查，部署后的修复纳入版本与记录。

建造者维护方法、资料、工具和连接；执行者按当前依据和权限完成任务；判断者核实事实、专业质量与适用性，决定采用、补证、退回或升级；管理者处理资源冲突和跨岗位依赖；决策者按授权决定重要投入、承诺与经营取舍。同一人可以兼任，服务和程序按实际能力承担相应工作。

读取什么、可以写回什么、能够执行哪些动作，落实到具体对象与工具。资料缺失、条件冲突或执行失败时，任务交出已完成内容、受阻位置和未决项，由约定人员接手。单次、定时或业务变化触发的任务按实际需要配置，持续运行另验触发依据、频率和异常接管。

工具部署后，让真实使用者完成约定工作，留下采用、退回和原因。功能正确却增加录入、核验或下游积压时，沿原任务查清方法、资料、工具和资源条件。试运行交付运行版本、实际任务记录、问题处理与维护接手。按已批准的蓝图与计划逐项确认完成、部分完成和未完成范围；范围调整须说明原因并重新确认。

[澳洲乳企](../下册-案例汇编/C-制造业/C11-澳洲乳企海外动销分析.md#c-24-f01)据实施者自述，先在已有系统上跑中国一条产品线，要求数字能追源、结论进入周会，跑通后再接越南，属于局部使用。原系统、AI抽取与人工确认各有分工。周会采用之后，预算决定与业务结果继续观察。

<a id="section-2-4"></a>
## 2.4 核算完整投入，验收实际结果

### 沿目标、蓝图和计划分层验收

验收要求在确认目标和编制计划时约定，随建设节点、试运行和业务观察分别完成。负责人用真实记录核对：目标所需成果是否建成，产物是否合格并被接手，后续业务发生什么变化。尚未完成的范围保留状态和责任。

| 验收范围 | 检查什么 | 依据及确认责任 |
| --- | --- | --- |
| 建设与集成 | 数据模型、应用工具、设备网络、接口权限及异常接管符合蓝图与项目包约定。 | 交付版本、样本、联调、专业核验与现场试运行；建设、专业及维护负责人确认。 |
| 任务与采用 | 产物合格，接收者实际使用，变化进入后续工作。 | 合格、退回、采用、返工、等待和执行回执；判断者与接收方确认。 |
| 业务结果 | 2.1约定的交付、质量、库存、资金或客户目标发生什么变化。 | 固定对象、范围、质量、观察期与截止日，解释同期变化；业务负责人核对。 |
| 服务贡献 | 可比基础条件下，新增服务具体改变什么，增加哪些投入。 | 同类任务比较或分步接入，记录原模块和其他措施的作用；按证据范围判断。 |

基础模块与服务同时补建时，项目整体改善与服务增量分别判断。参考架构、官方目标和其他企业成绩用于选方案，本企业结果使用自己的基线与运行记录。没有可比依据时，保留已观察变化和机制分析，净贡献继续验证。

### 从调用价格核算到完整交付成本

模型调用价格只对应服务使用的一部分支出。较低调用支出可以支持多轮需求整理、编码、测试和方案试验，部分开发与试验成本有机会下降；完整经济性还取决于工程质量、采用、返工与维护。每个企业按实际建设与运行核算，不预设统一成本降幅。

一次性投入包括资料整理、方法验证、开发配置、设备及网络、系统连接、培训和权限准备。持续投入包括执行、平台及服务、调用、人工判断、交接、返工、异常处理和维护。失败尝试与修复保留，共用投入归集一次。人工工时、模型用量和现金支出分别记录，再按实际成本和计费规则核算。

本轮预算覆盖建设及计划运行支出，可复用建设仍计入当期现金需求。比较期间经济性时，对可复用建设说明分摊期间与规则，同一核算不重复计入完整支出及其分摊。同等范围、质量和数量下比较总投入；数量变化时，用相关投入除以合格交付数量比较单位成本，并保留规模、任务难度及条件差异。

[温州连锁烘焙企业](../下册-案例汇编/F-批发与零售业/F11-温州连锁烘焙企业AI经营管理.md#s-31-f02)经营者称，会前填报与口径检查增加，老板制作的原型由开发人员继续完善和兜底，属于局部使用。会议准备前移和工具维护都进入完整投入，减少会中时间放回同一范围比较。

节时、总周期、成本替代、覆盖范围和承接容量分别表达，再观察它们是否进入有需求且能兑现的业务。释放员工时间与工资现金支出减少分别核实，销售额、毛利和净利润使用各自依据。

## 2.5 根据反馈决定扩展、调整或停止

运行与验收记录返回目标和建设安排。分析任务要查清原因假设是否核实、建议为何被采用或退回、实际动作是否发生、结果是否符合预期。依据错误、推理不适用、行动未执行和执行后无效，由不同责任人继续处理。

业务人员补证，建造者修订资料、规则、工具或模型，管理者处理资源与接手，有权者确认改变的范围。修订保留前后版本，用原失败样本和后续相近任务再验证。资料积累、人工维护和模型适应性调整按实际发生分别记录，持续记录本身不等于能力已经改善。

可靠交付、实际采用且完整投入合理的范围可以保留或扩大。扩展到其他客户、门店、产品线或任务时，重新核对输入、规则、连接、权限和质量条件，确认判断与接收能力足以承接新增数量，并更新蓝图、项目包、预算与复核时间。

采用不足时，先检查是否增加录入、产物不适用、规则不清或缺少指导。能够定位和修正的，明确责任与期限后重新验证。持续没有实际使用、核验返工抵消改善、关键条件无法取得或异常无人接手的范围，提交减少或停止投入的决定。

[消防维保企业](../下册-案例汇编/M-科学研究与技术服务业/M02-消防维保企业数字化项目取舍.md#c-13-f01)据实施者自述，确认监管系统没有开放接口后，采用既有工具和小模块，叫停约十万元的一笔计划采购。已发生的是局部数字化使用与采购取舍，AI辅助月检描述仍属于方向。外部约束改变了建设选择，已有数字化投入继续按用途保留。

停止时交回未完成任务和客户责任，安排业务接回，保留可复用产物与原因记录，停用失效能力。新的证据和条件形成后，再由现状、目标、蓝图与计划开始下一轮确认。
